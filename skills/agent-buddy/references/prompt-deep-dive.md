# Prompt 深度技法

RCTFC 五段式的深化与场景挂载。场景检测命中后按需加载对应章节。

---

## Part A: RCTFC 深化

### 背景三问（C₁ 段）

用户写 Context 段时，引导他回答三个问题，填完 C₁ 段自然有深度：

1. **给谁看？**（受众身份 → 决定语言层级。同事 ≠ 老板 ≠ 客户）
2. **在哪用？**（行业/场景 → 决定领域知识。B2B SaaS ≠ 快消 ≠ 制造业）
3. **为什么做？**（目标 → 决定侧重点。汇报 ≠ 说服 ≠ 记录）

**示例**——差 vs 好：

```
❌ C₁: 我是产品经理
✅ C₁: 我是 B2B SaaS 公司 PM，产品月活 50 万，面向直属老板写周报，老板关注留存和收入
```

诊断时若发现 C₁ 段只写了身份没写受众和目的，用上述三问引导用户补充。

### 约束优先级（C₂ 段）

当用户的约束之间冲突时（如"详细但要简短"），教他区分两类约束：

- **硬约束（不可退让）**：格式、字数上限、禁止项。AI 一旦违反，输出不可用
- **软约束（可协商）**：语气、风格、深度。可以让步，不影响可用性

**冲突规则**：硬约束优先。同时教用户：正面指令在前，反面约束在后——先说"写成 200 字短文"，再说"不要啰嗦"。

### 角色设计法（R 段）

用户写 Role 时常写"你是一位专家"——太宽，不起作用。引导他把 Role 填三个维度：

```
好 Role = 领域 + 视角 + 风格

❌ 你是一位营销专家
✅ 你是一位在 B2B SaaS 做了 5 年内容营销的负责人，擅长用数据讲故事，讨厌空洞的 buzzword
```

三个维度填满后，Role 从无意义的标签变成真正的视角锚点。

## Part B: 场景技法

以下技法在场景检测命中时融入三档改写。未命中时不加载。

### BAB 说服链（营销场景）

> 源自广告文案行业经典方法论（Before-After-Bridge）

触发词：文案 / 种草 / 推广 / 广告 / 卖点 / 营销 / 促销 / 带货 / 品牌

**技法**：BAB = Before → After → Bridge，经典广告文案说服结构。

融入 RCTFC 的方法——把 BAB 嵌入 Task 段：

```
T: 请用 BAB 结构写文案。
   Before：目标用户现在的痛点/困境（1 句话）
   After：使用产品/服务后的理想状态（1 句话）
   Bridge：怎么从 Before 到 After——产品怎么解决问题（2-3 句）
```

改写时 Lite 版用简化 BAB（痛点+方案），Standard 版用完整三段，Pro 版加情绪渲染。

### 多视角对比（决策场景）

触发词：选哪个 / 对比 / 方案比较 / A 还是 B / 利弊 / 权衡 / 方案评估 / 帮我决策

**技法**：让 AI 从至少 2 个不同立场分析同一问题，最后给共识结论。

融入 RCTFC 的方法——加在 Constraint 段：

```
C₂: 请同时从 [立场A] 和 [立场B] 两个角度分析，各给出 3 个论证点，最后给出平衡后的建议。不要只站一边。
```

和 `references/advanced-techniques.md` 中「角色对话法」思路相通——前者是通用进阶技巧，本技法是决策场景的专门化应用。

### 指令-数据分离（喂数据场景）

触发词：帮忙分析这段 / 总结这篇文章 / 翻译下面 / 根据以下数据

**技法**：用分隔标记把指令和数据物理隔开，避免 AI 混淆。

```
[指令]
RCTFC 结构化 prompt...

[数据]
（粘贴的文本/表格/代码）
```

反面示例：指令和数据混在同一段里，AI 可能把数据内容当成指令的一部分去执行。

## Part C: 通用锦囊

### Prompt 测试法（含 Agent 实测模式）

用户写了一个 prompt 不确定好不好时，教他跑最小测试：

> 同 prompt 跑 3 次，看输出方差。
> 方差大 = 约束不够（R/F/C₂ 需加强）
> 方差小但方向都偏 = Task 方向错了（T 需重写）

不用教统计学概念，用大白话说"跑三次看看是不是每次都差不多"。

**Agent 实测模式**（陪练自己动手测，opt-in）——进入条件见 SKILL.md「实测模式」：用户明确要求 + 宿主提供执行工具（web_search / shell / 代码执行）+ 范围限本次改写版。做法：

1. **方差测试**：把改写版原样执行 3 次，对比输出。方差大 → 约束不够，建议收紧 R/F/C₂；方差小但方向都偏 → T 段方向错，重写任务描述。
2. **事实核查**：改写版涉及的数字、引用、API 名，用 web_search 或执行工具验证存在性和准确性；查不到的如实说"此项未能核实"。
3. **代码验证**：改写版含代码时，直接在沙箱/终端跑一遍，把报错和修正写进诊断。
4. **结果并入诊断**："3 次输出第 2 次格式跑偏 → F 段还要收紧"——实测结论和五维诊断同样可信，且更有说服力。

红线照旧：不替用户做业务决策、不说"这样一定能得到好结果"、未核实项如实标注。

### 多 Prompt 编排

当用户一个 prompt 里塞了 ≥3 个不同动词（分析 + 写 + 翻译 + 总结...）时，建议拆成多个 prompt。

三种典型链式结构：

```
调研链：信息收集 → 分析提炼 → 结论输出
创作链：大纲框架 → 内容填充 → 风格润色
分析链：数据清洗 → 模式识别 → 洞察建议
```

每步确认后再往下，不一次到位。
