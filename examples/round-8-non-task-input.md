## 输入

```

```

## 按旧规则会怎么判（R4 立规前）

五维逐项：role 0 · context 0 · task 0 · format 0 · constraint 0 → 缺失 5 个 ≥ 3
→ R3 → **无效 0/10**。

这个结论**公式没错、对象错了**：五维量的是「任务交代得够不够」，而「我很好」
里没有任务。等于给一句问候打不及格分——不是它写得差，是它根本不在这场考试里。

## 按新规则（v1.8 / R4）

Provider 第 0 步可判定性检查 → 形态判定为「状态陈述 / 社交回合」→
`judgeable = false`、`dimensions` / `total` = null（不估填）→ 规则层 R4
→ **无法判定**。

```
判定：**无法判定** ｜ 参考分 未评估 ｜ 未命中 R0-R3（R4：输入不构成可判定对象） ｜ 未做工作空间验证
```

### 严格风格下的答复（节选，原文见 `workspace/bridge-20261029-3/answer.md`）

> ## 这不是提示词。三个字里没有请求，判不了
>
> 【纠正方向】
> - **要判，先给它一个请求**：想让 AI 接话就明说——「我最近状态不错，随便问点什么」。
> - **别把社交回合当指令**：「我很好」是回问候的，它的有效性由上文决定，不由我判。
> - **要判聊天记录，贴完整来回**：对方问了什么 + 你怎么答的。
>
> 下次贴之前先问自己一句：我这是在**要东西**，还是在**聊天**？要东西才有判定对象。

## 三种「无法判定」的病因必须分开说

| 出口 | 触发 | 病因 | 用户该做什么 |
|---|---|---|---|
| R0 | 未获合规 JSON 摘要 | 后端没交结果 | 重来一次 |
| R4 | `judgeable = false` | 输入不是请求 | 补一个请求，或贴完整来回 |
| （R1/R2） | 歧义 / 矛盾 | 出口是「无效」，不是无法判定 | 先澄清 / 先取舍 |

R1/R2 的红线出口是「无效」——它们判得动，只是判死了。R0/R4 才是「判不了」，
但原因一个是系统故障、一个是对象不成立。

## 教学点

1. **判定前先判「能不能判」**：判定器的第一道工序不是打分，是确认对象存在。
2. **全 0 是危险信号**：五维同时 0 分时先怀疑对象错位，再怀疑输入差。
3. **「有效」不只是「信息够」**：社交回合的有效性取决于上文承接得顺不顺，
   单句脱离上下文无从评价——这也印证了 ROADMAP 里 v2 对话循环的必要性。
