# 子会话宿主模式（v0.3 · 2026-10-29 默认 L2）

> 状态：试验性。v0.1 把接单管道做成 LLM-free（`serve.mjs`）；v0.2 加三级判定调度链；
> **v0.3 定默认路径 = L2（主会话判定）**，L1（外部 CLI agent 自动判定）降为备用并标注未验证；
> 新增**本地接单账本 + 待回推清单**（`scripts/lib/ledger.mjs` / `scripts/pending.mjs`），
> 修掉 L2 最真实的故障——「被唤醒后丢了 id / 不确定推没推」。
> 改动集中在 `scripts/` + `prompts/` + 文档；`server/` `web/` 始终未动。
> 定位：让「接单管道」「判定」「主线对话」三者解耦，判定内容不挤占主线。

## 1. 为什么要有这个模式

面板桥（`render_bridge_view`）挂在当前会话时，会同时承担两件事：主线对话 + 长挂等单。判定
任务插进主线，上下文被判定内容挤占，隔天回看也乱。子会话宿主把这两件事拆开。

## 2. 与现有两种宿主的关系

| 宿主类型 | 注册方式 | hostId 从哪来 | 适合 |
|---|---|---|---|
| 面板桥 | `render_bridge_view` | `ui/initialize` 的 `hostContext.workbuddy.sessionId` | 当前会话随手判 |
| 无面板宿主 | `host.mjs --id <x>` | 命令行显式指定 | 后台常驻、脚本化 |
| **LLM-free 消费者（本轮新增）** | `serve.mjs --id <x>` | 命令行显式指定 | **推荐**：心跳+接单一体、自终止窗口、不依赖 LLM 配额 |
| 子会话宿主（旧） | `host.mjs --wait` 由子代理拉起 | 命令行显式指定 | 已不推荐（见 §4） |

## 3. 为什么必须走 CLI 而非桥视图

子会话与初始会话共享同一条 MCP 连接、`sessionId` 相同。子会话若调 `render_bridge_view`，
只会注册成和主线同一个宿主，拿不到第二个身份。能拿到独立身份的只有显式 `--id`——它走
`POST /mcp` 的 `await_question`，身份由参数决定、与会话无关。

## 4. 实测结论（2026-10-29 本轮，先看这个）

- ⚠ **backlog 是否回放：两次实测不一致，不要依赖**。v0.1 曾观察到新订阅者秒接回孤儿待判
  （`5fe93e63…`，`本宿主待答 1` 立即返回）；v0.2 复测（同 host 已有 1 条待答、新起
  `serve.mjs`）观察 **45s 未接回**。结论：桥对同一 host 存在已读游标，**不保证重放**。
  → 降级 / 断档后的单必须**按显式 id 从 `inbox.jsonl` 接管**（见 §5.4），别指望重订阅自动接回。
- ❌ **真正的断点 = 把管道绑在 LLM 子代理上**：子代理会因配额 **429** 中途死掉（实测
  子代理 2 分钟时 429 退出），它一死，它拉起的 `host.mjs` 随之被杀，待判就成孤儿。
  **管道（等单/接单）根本不需要 LLM，只有判定才需要。**
- ❌ **timeout 坑**：`host.mjs` 内部 `mcpCall` 超时 = `waitMs + 20000`（默认 **75s**）。
  旧文档「Bash timeout 70000 + waitMs 55000」会让进程在 **70s 被 SIGTERM 误杀**，永远等不到
  一轮完整返回（实测三次均在 70s 被杀）。外层 timeout 必须 **> 75000**，或干脆用自终止窗口。
- ⚠ **网页下拉只列在线宿主 + 发送时自动回退**：只跑 `--wait` 时，每 55s 里有约 25s 处于
  离线显示窗口（`HOST_ALIVE_MS=30s`），此时下拉选不到它、发送会**自动回退到别的在线宿主**
  （如 `coach-local`）。必须有心跳常驻。

## 5. 标准做法：默认 L2（主会话判定），L1 备用

**核心分工**：`serve.mjs` 负责「接单 + 建任务包 + 调度」，全程 LLM-free；只有**判定**需要 LLM。
接单后按三级链依次尝试，前一级失败自动落到下一级：

| 级 | 谁判 | 触发条件 | 失败信号 |
|---|---|---|---|
| **L2** 主会话判定（**默认**） | 被唤醒的主会话（可下发短命子会话，或亲自判） | 未配 `--spawn-cmd`（默认） | 主会话也不可用 → L3 |
| **L1** 短命判定子会话（备用） | `--spawn-cmd` 指定的外部 CLI agent（如 `claude -p`） | 显式配了 `--spawn-cmd` | 进程非 0 / 没写稿 / 稿子过不了闸门 → 退出码 **4**，落回 L2 |
| **L3** 人工 | 人 | L1 + L2 都不通 | 按 `task-<id>.json` + `pending.mjs` 手动处理 |

> **为什么默认 L2**：L1 的正确性取决于外部 CLI 吃什么参数、认不认 stdin、有没有独立配额，
> 变量多且不在本技能控制内（本机 `claude` 只验到「进程能起、能读 stdin」，**真实判定链路未跑**，
> 会消耗用户额度）。L2 只依赖本会话 + 本地脚本，链路短、可观测、失败立刻可见。

### 5.1 默认路径：L2（一条命令接单，主会话判定）

```bash
node "<skill-root>\scripts\serve.mjs" --id coach-sub --label "教练 · 子会话" \
  --window-ms 600000 --mode wake
```

接单后以退出码 0 结束（wake 模式的退出事件用来唤醒 Agent），并打印五步指引：

```
=== 收到一条待判问题 ===
id      : e5678320-…
---- 消息原文 ----
风格：objective（客观）
范例：不要
—— 以下是我要判定的内容 ——
帮我把这个月的销售数据分析一下，做个总结。
---- 原文结束 ----
风格    : objective（客观）　范例: 不要　正文 21 字
TASK_READY id=e5678320-… style=objective example=0
  taskFile / promptFile / answerFile = …/…-<id>.*

--- L2 主会话判定（默认路径）---
① 读口径：SKILL.md · providers/free/SKILL.md · rules.md · styles.md（范例=要再加 generators.md）
② 读正文：…/body-<id>.txt（21 字，风格 objective）
③ 写稿到：…/sub-answer-<id>.md
④ 自检  ：node …/answer-check.mjs --file … --style objective
⑤ 回推  ：node …/reply.mjs --id <id> --file …
（另有单挂着 / 忘了 id → node …/pending.mjs）
```

判定纪律与主线完全一致（五步流程 → free Provider 五维 → rules.md R0-R4 → styles.md 渲染）。
写完稿 → 自检 → 回推：

```bash
node "<skill-root>\scripts\answer-check.mjs" --file "<answerFile>" --style objective
node "<skill-root>\scripts\reply.mjs" --id <id> --file "<answerFile>"
```

回推成功由 `reply.mjs` 记 `REPLIED` 销账（见 §5.8），无需手工登记。

### 5.2 备用路径：L1（外部 CLI agent 自动判定 + 自动回推）

```bash
node "<skill-root>\scripts\serve.mjs" --id coach-sub --label "教练 · 子会话" \
  --window-ms 600000 --mode wake \
  --spawn-cmd "claude -p --permission-mode acceptEdits < \"{promptFile}\""
```

> ⚠ 未在本机实跑验证「真实判定质量」。已验证的只有：spawn 失败 → 码 4；替身按
> `<` 读到完整 prompt（2667 字节、无残留占位符）→ 写稿 → 自动回推 → 码 0。
>
> ⚠ prompt 只能用 **`<` 重定向**送进 agent。写成 `$(cat {promptFile})` 会在 Windows 的
> cmd.exe 下**原样当字面参数**（实测：ARG 收到 `$(cat G:/…`、stdin 为空）→ 判定会话拿到
> 一坨无效 prompt。已实测 `<` 重定向在 cmd 与 Bash 下均正常（stdin 收到 1847 字节）。
> CLI 若不吃 stdin，就让 agent 按 `promptFile` 路径自己 Read——模板本来就要它读 `bodyFile`。

接单后 `serve.mjs` 自动完成：解析信封 → 写 `body-<id>.txt` / `task-<id>.json` → 用
`prompts/judge-subsession.md` 渲染出**可直接下发的子会话 prompt** → 执行 spawn → 校验产物过
质量闸门 → 合格则**自动回推网页**。

### 5.3 退出码（降级的机器信号）

| 码 | 含义 | 主会话该做什么 |
|---|---|---|
| 0 | 接到单，且（L2 无 spawn / L1 spawn 成功已回推） | **L2：判定 → 回推**；再起一个接下一单 |
| 3 | 窗口到期没接到单 | 正常；需继续就再起 |
| **4** | **接到单但 spawn 失败 / 产物不合格 → 需降级到 L2** | 读 `promptFile` 接管判定，**按显式 `--id` 回推** |
| 1 | 桥不在线 / 致命错误 | 先起桥 |

### 5.4 降级 / 断档后的单，用账本接管（别靠猜、别依赖 backlog 回放）

v0.2 实测：L1 失败留下待判后，重起 `serve.mjs` 观察 45s **没有**接回那单（桥对同一 host 有
已读游标）。所以降级单不会自己回来，必须**按显式 id** 接管：

1. 首选：`node "<skill-root>\scripts\pending.mjs"` —— 它把「磁盘上有任务单、账本里没有
   REPLIED」的单全列出来，附 `answerFile` 现状（缺 / 已写 N 字 / 闸门 PASS 或拒绝原因）
   和可直接复制的自检、回推命令（详见 §5.8）。
2. 备选：看 stdout 的 `DEGRADE id=…`，或 `workspace/_bridge/inbox.jsonl` 最后一条。
3. 回推**显式带 `--id`**，不要用 `--inbox-latest`（inbox 是流水，期间来新单会取错）。

### 5.5 质量闸门（回推前自动拦）

`reply.mjs` 与 `answer-check.mjs` 共用 `scripts/lib/answer-quality.mjs`，规则单一来源：

- **硬伤（拒绝推送）**：空稿 / 过短 / 占位符残留 `{{…}}` / TODO·待补充 / `<details>` 未闭合
- **提示（照推）**：缺 `<details>` 存档块 / 缺行动区
- **短稿宽松**：显式 `brief`，或 <80 字且不含 `<details>` → 不要求结论词与折叠块
  （但**只要出现 `<details>` 就必须闭合**，防折叠区渲染错乱）
- `--force` 可强推

### 5.6 组装件

| 文件 | 作用 |
|---|---|
| `scripts/serve.mjs` | LLM-free 消费者：心跳 + 接单 + 任务包 + spawn + 自动回推 |
| `scripts/lib/envelope.mjs` | 信封解析（风格/范例/正文）+ 任务单物化 + prompt 渲染 |
| `scripts/lib/answer-quality.mjs` | 质量闸门规则（单一来源） |

| `scripts/pending.mjs` | 待回推清单 CLI（断点恢复，§5.8） |
| `scripts/answer-check.mjs` | 闸门 CLI（子会话写稿后自检） |
| `prompts/judge-subsession.md` | 判定子会话 prompt 模板（占位符由 `renderPrompt` 填） |

### 5.7 L2 主会话流程（手写版，等价于上面的自动化）

1. 确认桥在线：`node "<skill-root>\scripts\bridge.mjs" --check`。
2. **Bash run_in_background** 起 `serve.mjs`，拿 task_id。
3. 告诉用户：网页下拉选「教练 · 子会话」再发送。
4. 后台任务完成通知到达 = 接到一单 → 读输出里的 `TASK_READY` / `DEGRADE` → 判定 →
   回推 → 再起一个接下一单。
5. 要「隔离不污染主线」就下发给**短命**判定子会话（判完即退）；**别让子会话驻留等单**——
   驻留等单正是 429 的致命点。

### 5.8 断点恢复：账本 + `pending.mjs`（v0.3 新增）

L2 的真实故障不是「判不出来」，而是**醒来后丢了 id**：上下文被压缩、后台任务通知被别的消息
挤走、或者干脆忘了回推。桥没有「列出待答」的接口（只有 `pendingCount` 计数），所以本地留账本。

**账本**：`workspace/_bridge/ledger.jsonl`，一行一事件，全部由脚本写、不依赖 LLM：

| 事件 | 谁写 | 含义 |
|---|---|---|
| `RECEIVED` | `serve.mjs` | 接单并建好任务包 |
| `DEGRADE` | `serve.mjs` | L1 失败，交 L2 |
| `REPLIED` | `reply.mjs` | 已推送到网页（含 duplicate），**唯一销账依据** |
| `DROPPED` | `pending.mjs --drop` | 人工放弃该单 |

**「待回推」定义**：磁盘上有 `task-<id>.json`，且账本里没有该 id 的 `REPLIED` / `DROPPED`。
故意以任务单为准而非 inbox——inbox 是流水，来新单就会取错 id（踩过）。

```bash
node "<skill-root>\scripts\pending.mjs"          # 人看
node "<skill-root>\scripts\pending.mjs" --json   # 机读（自带 bridgePending 做交叉核对）
node "<skill-root>\scripts\pending.mjs" --drop <id>
```

输出示例（含稿件现状，一眼判「推没推」）：

```
=== 待回推 1 条（按收单时间正序）===
桥全局待答：1 条

[1] id=e5678320-…
    风格 : objective（客观）　范例: 不要　正文 21 字
    原文 : …/body-e5678320-….txt
    稿件 : …/sub-answer-e5678320-….md → 已写 1339 字　闸门 PASS
    ① 自检: node …/answer-check.mjs --file … --style objective
    ② 回推: node …/reply.mjs --id e5678320-… --file …
```

退出码：`0` 无待回推 / `5` 有待回推。注意区分两种「挂单」：
`pending.mjs` 说「无待回推」但桥仍报 `pendingCount>0` → 说明那单**根本没被本机接走**
（宿主离线、或网页下拉选错了宿主），不是本地漏推。

## 6. 旧写法（仅存档，勿再用）

原来的「spawn 一个持久子会话跑 `host.mjs --wait --wait-ms 55000`、Bash timeout 70000、
空转重跑 3 次」：
- 会被 70s SIGTERM 误杀（外层应 > 75000）；
- 子代理 429 一死，管道全断。

→ 用第 5 节的 `serve.mjs` 取代；仍要 `host.mjs` 手动跑时，记得加 `--total-ms` 并给足外层 timeout。

## 7. 判定侧纪律（不变）

- 判定口径与主线一致（`providers/` + `rules.md` + `styles.md`），子会话是执行体，不是第二套标准。
- 只答一单 / 一窗口；重复提交服务端静默忽略（`duplicate`），不要重写。
- 不重启桥、不 kill 进程、不碰 `server/` `web/` `scripts/`。

## 8. 边界

| 项 | 现状 |
|---|---|
| 生命周期 | `serve.mjs` 窗口到期自退；wake 接一单即退；loop 窗口内连挂 |
| 接单窗口 | 由 `--window-ms` 决定、自动处理，无需猜 shell timeout |
| 串台 | `answer` 事件广播给所有 SSE 客户端，多窗口可能都看到（未改 web，已知） |
| 并发 | 不同 `--id` 互不冲突（`coach-sub`、`coach-sub-2`…） |
| 安全 | 桥默认只听 `127.0.0.1`；管道进程无额外权限 |

## 9. 排错表（更新）

| 症状 | 先查 |
|---|---|
| 网页下拉看不到子会话 | `serve.mjs` 是否在跑（心跳保在线）；`curl /web/state` 的 `hosts[]` |
| 发送报「无在线宿主」 | `serve.mjs` 已退（wake 接完一单 / 窗口到期）→ 重新起 |
| 收到问题但网页没反应 | 是否跑了 `reply.mjs --inbox-latest`；看其打印 |
| 子会话空转 / 被 70s 杀 | 换 `serve.mjs`（自终止窗口），别再用 70s 外层 timeout |
| 子代理 429 中途死 | 别把管道交给子代理；管道用 `serve.mjs`，判定用短命子会话或主会话 |
| 接到单却没自动回推 | 输出里找 `SPAWN_FAILED`；产物是否过闸门（`answer-check.mjs --json`） |
| spawn 退出 0 但网页没收到 | 是「假成功」：产物不合格被闸门拦了。别只看退出码，看 `SPAWN_OK` / `REPLY_FAILED` |
| 降级后那单不见了 | 桥不回放已读 backlog → 跑 `pending.mjs` 拿待回推清单，显式 `--id` 回推 |
| 稿子被拒「占位符残留 {{…}}」 | 模板变量没填全；改稿或 `--force` |
| `pending.mjs` 说没单但桥报 pendingCount>0 | 那单没被本机接走（宿主离线 / 网页选错宿主），不是本地漏推 |
| 判完忘了回推，隔天想不起来 | `pending.mjs` 会把它列出来（稿件「已写」但账本无 `REPLIED`） |
